# Makerstorage

Electronics-parts inventory manager for makerspaces/fablabs: components, categories, footprints, storage zones, stock movements, suppliers, purchase orders, project BOMs, low-stock alerts — scoped per organization (multi-tenant).

## Stack
- **Backend**: Rails 8.1 (8.1.4), **SQLite** in every environment (production too, with Solid Cache/Queue/Cable on separate SQLite DBs — see `config/database.yml`), Devise (auth), Inertia Rails.
- **Frontend**: Inertia.js + React 19 + TypeScript, Vite, Tailwind v4.
- **Components**: shadcn/ui (`new-york` style, `neutral` base color, Lucide icons) — see `components.json`.
- Ruby 3.4.12, Node 24+.

## Frontend conventions
- The entire frontend is built on **shadcn/ui**. Use the existing components in [app/frontend/components/ui/](app/frontend/components/ui/) as-is wherever possible.
- Avoid modifying shadcn component internals or hand-rolling custom one-off components when an equivalent shadcn/Radix primitive already exists — compose existing components instead. Don't add new raw `<button>`/`<input>`/`<select>` elements in pages; use the `ui/` equivalents.
- Only add a new component (via shadcn or from scratch) when nothing in the current library covers the need.
- Pick a storage zone with `StorageLocationSelect` (`components/storage-location-select.tsx`: searchable tree over path and code, optional inline create) and a category with `CategorySelect`, never a flat `Select` of zones.
- UI language is **English-first**. (There is a French-language design prototype in `design-makerstorage/` — treat it as a layout/behavior reference only, not a copy/language source.)
- **Translations (English + French)**: wrap every UI text in `t('English text')` from `@/lib/i18n` (`tn(one, other, count)` for plurals, `tx`/`txn` when a value is a React node), use `intlLocale()` in `toLocale*` calls, and add the French text to `app/frontend/locales/fr.json` (keyed by the English text; plurals as `{one, other}` under the English plural). `bin/rails i18n:frontend` lists missing/unused keys and `test/lib/translations_test.rb` fails on them. Labels in module-level constants are getters (`get label() { return t('…') }`) so they follow the locale. French copy says *composant* (not "pièce"), *Réglages* for Settings (*Paramètres* is kept for part parameters), and uses a non-breaking space before `? ! : ;`.

## Backend conventions
- Domain controllers `include Auth` and run `before_action :verify_organization_access`, then gate mutations with `verify_organization_writer` (blocks viewers), `verify_organization_admin`, or `verify_organization_owner` (all in `ApplicationController`).
- Always look records up through the tenant: `current_organization.parts.find(params[:id])`, never `Part.find`.
- Select-input payloads (categories, footprints, tags, suppliers, storage locations) come from the `OptionListSerializers` concern — reuse it rather than re-serializing.
- Return validation errors to Inertia forms with `inertia_errors(model, as: :resource)` so keys match the nested form data (`part.name`).
- **Locale**: `ApplicationController#switch_locale` uses `users.locale` (Profile → Language) or else the browser's `Accept-Language`, English by default; it's shared with the React app as the `locale` prop. Flash messages are `t("flash.<controller>.<key>")`, model errors `errors.add(:attr, :symbol)` (messages under `activerecord.errors.messages`), service errors `I18n.t("errors.…")`, all in `config/locales/app.en.yml` + `app.fr.yml` (same keys, checked by a test; missing translations raise in tests). Mails render in the recipient's locale (`User#send_devise_notification`, `NotificationMailer`). Left in English on purpose: data written to the database (movement reasons, generated names), CSV headers, MCP/OAuth API messages.
- **Every foreign key needs a matching `has_many … dependent:` on the parent** (`:restrict_with_error` when the child is history/ledger data). A missing one turns `.destroy` into an `ActiveRecord::InvalidForeignKey` 500 (SQLite enforces FKs).
- **Auth hardening**: Devise `:lockable` (10 failures → 15-minute lock, time-based unlock) plus per-IP `rate_limit` on sign-in, password reset, and sign-up (store: `ApplicationController::AUTH_RATE_LIMIT_STORE`; tests get a real store via `config.x.rate_limit_store`, cleared before each test). The reset form answers identically for known and unknown emails; changing the sign-in email requires the current password. **Email verification** (Devise `:confirmable`, on whenever mail can be sent — `config.x.email_verification`, off in production without SMTP): unconfirmed accounts sign in and use their own organization, but invitations are hidden and refused until `User#can_answer_invitations?` (a confirmed address); a sign-in email change waits in `unconfirmed_email`. `create_user` in tests is confirmed by default (pass `confirmed_at: nil`); `with_email_verification(false)` simulates an install without SMTP. Deleting a catalog supplier (Mouser/DigiKey/LCSC) disconnects the integration and is admin-only.
- **Content Security Policy** (`config/initializers/content_security_policy.rb`) ships **report-only** unless `CSP_ENFORCE=true` (opt-in per install); browsers post violations to `/csp-violations` (`CspReportsController`, logged as `[CSP] …`) in both modes — check those logs before enforcing. Inline `<script>` tags must use `nonce: true` / `request.content_security_policy_nonce`; new external origins (fonts, images, APIs called from the browser) must be added to the policy. Hotlinked part images are limited to `Makerstorage::SUPPLIER_IMAGE_HOSTS` (Mouser/DigiKey/LCSC), both in `Part#image_source_url` and in `img-src`. HTTPS is opt-in via `FORCE_SSL=true` (production), since LAN installs run on plain HTTP.
- Test helpers that read Inertia props parse `<script data-page="app" type="application/json" …>` — keep the `[^>]*` in that regex (the tag carries a nonce).
- Multi-record writes triggered by one action (purchase-order batches, bulk actions, CSV import rows) run in a transaction and turn `RecordInvalid` into a flash message rather than a 500.
- Roles per membership: `owner` > `admin` > `member` > `viewer`. Only **active, accepted** memberships grant access (`user.organizations` and the `*_of?` helpers go through `active_organization_memberships`, i.e. `OrganizationMembership.granting_access`). Adding a member from the Members page creates an **invitation** that grants nothing until the invitee accepts it from their profile (`InvitationsController`), within `OrganizationMembership::INVITATION_VALIDITY` (30 days; inviting the same email again renews an expired one); memberships created directly (signup, new organization, seeds) carry no invitation. An organization must always keep at least one active owner.
- `Organization`'s `has_many … dependent: :destroy` declarations run in declaration order: records that reference others (movements, projects, orders) are declared before what they reference (parts, locations, suppliers). Keep that order when adding associations.

## Domain notes
- **Multi-tenancy**: every domain record (parts, categories, footprints, tags, suppliers, storage locations, stock movements, orders, projects) belongs to an `Organization` via `organization_id`. `current_organization` is resolved per-session in `ApplicationController`.
- **Signup auto-creates a personal organization** for every new user ([app/models/user.rb](app/models/user.rb) `create_personal_organization`) — this is intentional, self-serve onboarding. Don't change this to an invite-only model.
- **Stock-per-location tracking**: `storage_locations` (self-referential zone tree: room/cabinet/shelf/bench/drawer/box) and `part_storages` (part × location quantity). `StockMovement` is the append-only ledger; creating one updates the corresponding `PartStorage.quantity` in a single atomic `UPDATE` (race-safe), and blocks overdraws unless `organization.allow_negative_stock`. Never write `PartStorage.quantity` directly — always go through a movement.
- **Purchase orders**: `Order` / `OrderLine` (supplier orders). Status flow `pending → shipped → received` via `Order#advance!`; `cancelled` sits outside that flow. Reaching `received` credits stock (`receive_into_stock!`) — once per order. A model validation enforces this: `received` and `cancelled` are terminal, and `received` is only reachable through `advance!`. An order holds one line per part: adding a part already on it tops that line up (`OrderLinesController#line_for`, like `import_project`). `OrderLineAllocation` splits a line's received quantity across storage zones (empty = fall back to the part's first location; otherwise must sum to the line quantity).
- **Projects**: `Project` / `ProjectLine` hold an imported BOM (`BomParser`; KiCad netlist XML, KiCad/EasyEDA BOM CSVs via `BomParser::Kicad`, resolved by `BomParser::Matcher`: MPN → SKU → supplier SKU → value + footprint → name, always within the organization) matched against parts for availability checks, order generation, and builds. A part can appear on several lines, so every decision (buildable, build deduction, ordering shortfalls, importing into an order) goes through `Project#required_by_part` / `#shortfall_by_part`, never per-line `ProjectLine#shortfall`. A project can also hold its **KiCad files** (`Project#kicad_files`: KiCad files typed by name as `application/x-kicad` by `Project.kicad_content_type`, or a project ZIP; `ProjectFilesController`); its BOM is then read from the `.kicad_sch` sheets, loose or zipped (`ProjectKicadFiles` → `BomParser::KicadSchematic`, KiCad 6+, one count per reference across hierarchical sheets). "Update BOM from schematic" goes through `Project#replace_bom!`, which keeps hand-picked parts (`BomParser.line_key`) and sends the project back to draft, unreserved. A project can instead be **linked to a GitHub repository** (`projects.github_repository` "owner/name", optional `github_ref` and folder `github_path`; `ProjectGithubController`, or "From GitHub" in New project): `ProjectGithubSync` resolves the ref to a commit (`GithubClient`, which only talks to api.github.com and follows archive redirects to codeload.github.com), downloads the repository ZIP, keeps the KiCad files under the folder as one ZIP attachment marked with blob metadata `github_sha` (replaced on each fetch; hand-added files stay), and replaces the BOM only when the schematics changed. Same commit = nothing downloaded. Private repositories use the organization's encrypted `github_token` (Settings → Integrations, write-only, left out of backups). No webhook or scheduled sync: updates are on demand.
- **Stock reservations** (Settings → Inventory, `organizations.stock_reservations_enabled`, on by default): a confirmed project with `reserved_at` set holds its BOM quantities (confirming reserves; Reserve/Release buttons; building releases). `Project#shortfall_by_part` counts physical stock minus what projects reserved *before* this one (`Project.reserved_quantities`, first come first served, floored at zero) so two projects never over-order the same stock. Reservations are bookkeeping only: they never write the ledger or block a stock movement, and turning the setting off ignores them without clearing `reserved_at`.
- **Stocktakes** (cycle counts, `Stocktake` / `StocktakeLine`, Stocktakes page): a count of one zone (plus its sub-zones by default). Starting one snapshots the zone's non-zero `part_storages` as lines; counting (typed, or `POST /stocktakes/:id/scan` with the shared `ScanCode` lookup: a zone code picks the zone being counted, a part code opens its line or adds one, `increment` counts one more) refreshes each line's `expected_quantity` to the stock at that moment, so movements made during the count survive. `Stocktake#complete!` writes one `adjustment` movement per counted difference (reason `Stocktake::MOVEMENT_REASON`, reference = the stocktake's), all or nothing, optionally taking uncounted lines as empty; a completed stocktake is read-only and kept as the report (CSV export), an in-progress one can be discarded. Two in-progress counts can't overlap a zone. A blind count hides `expected_quantity` of uncounted lines. "Zones due for a count" = zones holding stock that no completed stocktake covered within N days (`Stocktake.last_counted_at_by_zone`).
- **Loans** (`Loan` / `LoanLine`, `LoansController`, sidebar "Loans"): tools and parts lent to an active member (`borrower`, name copied to `borrower_name`) or anyone by name. `Loan#lend!` saves with a generated `LN-YYYYMMDD-N` reference and writes one `out` movement per line from its zone, all or nothing; `#return_items!` / `#return_all!` write `in` movements (default zone: the line's, then the part's fallback) and `#write_off!` records lost/used-up items with no movement. Settling row-locks the loan; it closes (`closed_at`) when nothing is outstanding. Overdue is computed (`due_on` < `Organization#local_date`, `Loan.overdue_on`), never stored: sidebar badge (`overdue_loans_count`), digest section (`notify_overdue_loans`), MCP `list_loans`. Default due date: `organizations.default_loan_days` (Settings → Inventory). Low-stock alerts count only what's on the shelf (lent items are out of stock). Backups drop `borrower_id`/`lent_by_id`.
- **Prices**: unit prices (`parts`, `part_suppliers`, `order_lines`) keep 4 decimals (show them with `formatUnitPrice` from `lib/money.ts`); order totals keep 2. A supplier link holds quantity **price breaks** (`part_suppliers.price_breaks`, JSON `[{ "quantity", "unit_price" }]` normalized and sorted by `PartSupplier`, filled from Mouser/DigiKey/LCSC lookups as `PartResult#price_breaks`); `PartSupplier#unit_price_for(quantity)` / `Part#order_unit_price(supplier_id, quantity)` pick the break, and order lines follow it when their quantity changes unless the price was typed (`OrderLine#follow_price_breaks`). **Price history** is read from order lines (`Part#purchase_price_lines`, cancelled orders left out), no table of its own. **Stock value** page (`/stock_value`, `StockValuation`): current price, last or average price of received orders, by category, top-level zone and part, plus CSV.
- **Consumption & suggested thresholds** (`PartConsumption`, Alerts → Suggested thresholds at `/alerts/thresholds`, `ThresholdSuggestionsController`, plus a Consumption block in the part sheet and `consumption` in MCP `get_part`): usage = "out" movements over `organizations.consumption_window_days` (90), minus zone moves, bag changes and duplicate merges (recognised by their reasons, `TRANSFER_REASON_PATTERNS`: keep a new transfer's reason in that list) and loan outs (by loan reference); adjustments don't count. The daily rate is spread over the part's history (first movement), clamped to 14 days…window. The suggestion holds `threshold_cover_days` (30) of use, or the preferred supplier's (else the part's) lead time + 7 days when longer, and needs 2 uses in the window. Nothing is stored: computed on read, and writers apply suggestions (recomputed server-side) to `min_stock_threshold`.
- **Reordering** (alerts, project shortfalls) subtracts what's already on open orders (`Order.incoming_quantities`, pending + shipped), so repeat clicks don't double-order.
- **Generated references** (`Order.next_reference`, `Project.next_reference`, `Stocktake.next_reference`) must be saved with `save_with_generated_reference! { … }` (`GeneratedReference` concern), which redraws on a concurrent clash instead of 500ing.
- **Attachments** go through `AttachmentValidation` (`validates_attachment :name, content_types:, max_size:`); add a limit for any new `has_one_attached` / `has_many_attached`. A part's own files (`Part#attachments`, any type via `AttachmentValidation::ANY_TYPE`, 50 MB each, `Part::MAX_ATTACHMENTS`) are added and removed from the part sheet by `PartAttachmentsController`, which also removes the supplier `datasheet` the sheet lists with them; `PartMerge` moves them (a second datasheet joins them). Files are served only to members of the owning organization by `StoredFilesController`: link them with `stored_file_path_for(attachment)`, never `rails_blob_path`/`url_for` — every `/rails/active_storage/*` route is shadowed with a 404 in `config/routes.rb`, and orphan blobs are purged daily (`PurgeUnattachedBlobsJob`). A new attachable model must expose `organization_id` (or be `Organization`) for `StoredFilesController#readable?`.
- **Inventory list** (`PartsController#index`) is paginated on the server by `PartsIndexQuery` (search, category, facets, sort, 50 per page over light plucked rows); the page gets one page of parts plus `matching_ids` for cross-page selection, and fetches parts beyond the page via `POST /parts/rows`. Add new list filters there, not in the React page.
- **Parameters** (`ParameterDefinition` / `PartParameter` / `CategoryParameter`, Parameters page at `/parameters`): an org's technical parameters, `number` (with a unit) or `text`. Number values are typed like BOM values ("4k7", "100nF", "1/4W", "3V3") and parsed by `ParameterValue` into `numeric_value`, stored in the unit itself (no prefix) and shown canonically ("4.7 kΩ"); changing a definition's type or unit recomputes them and is refused if one no longer reads. A category's template (`Category#parameter_template=`, inherited by sub-categories: `Category.parameter_templates`) is what the part form proposes. The part form sends `part[parameter_values]` (definition id => text, "" removes; the controller drops other orgs' ids). `Part#sync_parameter_fields` keeps the old Tolerance / Voltage rating / Power rating columns and the parameters of those names in step both ways (a parameter changed in the same save wins), and fills the template's first Ω/F/H parameter from the free-text Value (never the reverse); the form hides those three inputs once the parameters exist. "Add standard parameters" (`ParameterDefinition.install_standard!`) adds the standard set, templates categories by name (English and French) and fills parts from their fields; it is not run on new organizations. List filters: `param[<id>][min|max]` / `param[<id>][values][]` in `PartsIndexQuery` (inclusive bounds, unreadable bounds ignored and flagged), plus columns for the selected category's template.
- **Alternatives** (`PartAlternative`, part sheet → Alternatives, `PartAlternativesController`, writers link; the picker searches on the server, `?q=`, 20 at a time): two parts of one organization that can stand in for each other, stored once per pair with the lower id in `part_id` (`PartAlternative.link!`) and read both ways (`Part#alternative_links` / `#alternative_parts`, `PartAlternative.involving`). `PartEquivalents` suggests unlinked ones on read (nothing stored): same category, unit and footprint (when both have one), not obsolete, every key parameter the candidate has (the category template's, else all the part's) equal, or better for ratings (`AT_LEAST`) and tolerances (`AT_MOST`), with at least one defining parameter equal; a part without parameters falls back to the same Value + footprint. A project's short lines list linked alternatives with stock it can count on (minus earlier reservations) and "Use" re-points the line; MCP `get_part` lists `alternatives` and `suggested_equivalents`, `check_bom` short lines their stocked `alternatives`. Merges fold links (`PartAlternative.fold`), backups carry them.
- **QR labels** (`app/frontend/lib/labels.ts`, printed from the parts bulk bar and the zone header) encode `<origin>/scan?code=…` with the part's IPN/barcode/SKU (else `part:<id>`) or the zone's code (else `zone:<id>`). `ScanCode.normalize` strips such links back to the code whatever host printed them, and `ScanCode#part` matches IPNs before barcode/SKU/MPN (shared by the Scanner page and stocktake counting); keep label codes and lookup in sync. **Network label printers** (`LabelPrinter`, Settings → Label printers, admins manage, members print): the browser renders each label as a 1-bit bitmap at the printer's `#geometry` (`lib/label-bitmap.ts`, turned a quarter when longer than wide) and posts it to `LabelPrintersController#print`, which checks its size and sends it raw over TCP: Brother QL raster (`LabelPrinting::BrotherQl`, 720-dot heads, DK rolls in `MEDIA`) or ZPL (`LabelPrinting::Zpl`). `LabelPrinting::Network` only connects to private/CGNAT addresses on printer ports (9100–9109, 6101), pinned to the checked IP; `NETWORK_PRINTING=false` turns it off. Printers are settings: kept by a reset, carried by backups, dropped by a merge.
- **Supplier bag labels**: `SupplierLabel.parse` reads the ECIA / ISO 15434 DataMatrix on DigiKey and Mouser bags (plus the `{GS}`-style stand-ins keyboard scanners type) and LCSC's QR code; `ScansController#lookup` tries it before part/zone codes (`ScanCode`) and matches customer PN → IPN, supplier PN → `sku` / `part_suppliers.supplier_sku`, then MPN. Receiving (`POST /scan/receipts`) is one `in` movement with `LABEL_REASON` and the reference `"<Provider> <order>"`, which flags a rescan of the same bag; it never touches orders (open ones are shown as a double-count warning). An unknown bag opens the add-part dialog through `/parts?new=1&prefill[…]`, and `return_to=scan` brings the create back to the scanner.
- **Offline scanner** (`lib/offline-scanner`, `hooks/use-offline-scanner.ts`): the Scanner page downloads `GET /scan/offline` (`OfflineScanSnapshot`: every part's codes and stock per zone, zones, open order lines, a year of bag receipts, plus a fresh CSRF token) into IndexedDB per user and organization, and when the server can't be reached answers scans on the device with `OfflineLookup` (a port of `ScansController#lookup` / `ScanCode`, and of `SupplierLabel.parse` in `supplier-label.ts`: **keep both sides in step**). Counts and bag receipts made meanwhile wait in a per-user queue (stock shown includes them) and go to `POST /scan/sync` (`OfflineScanSync`, writers only, same reasons as online), one movement each, stamped with the device's `offline_uuid` (unique per org, so a retried sync never writes twice) and `scanned_at`; refused scans stay listed until discarded. Actions that need the server (part sheet, zone page, stocktakes, creating a part) are hidden offline. `app/views/pwa/service-worker.js` (registered by the Scanner page, HTTPS/localhost only) keeps a copy of `/scan` and its assets so the page reopens offline; logging out drops the snapshots and that copy, not the queue.
- **CSV imports** go through `BomParser.each_row`, which accepts UTF-8 (with or without BOM) and Windows-1252 (French Excel's default).
- **Order line splits**: changing an `OrderLine`'s quantity drops its `OrderLineAllocation` split (`after_update` callback), and `receive_into_stock!` credits any unsplit remainder to the fallback location.
- **Supplier catalogs**: `SupplierCatalog` (Mouser, DigiKey, LCSC) for part lookup, order import, and Mouser cart push. API keys and DigiKey OAuth tokens are stored encrypted on `Organization`. LCSC has no key: its official API is partner-only, so `SupplierCatalog::Lcsc` uses the keyless endpoints behind lcsc.com (unofficial, may break) and is opt-in per org (`organizations.lcsc_enabled`, Settings → Integrations); LCSC prices are USD and only fill the unit price for USD orgs. Remote asset downloads go through `SupplierCatalog::RemoteFile` (SSRF-guarded) — don't fetch supplier URLs any other way.
- **Organization backups** (`OrganizationBackup`, Settings → Backup): admins export the current org as a ZIP (`data.json` with source ids, a CSV per table, Active Storage files); any signed-in user restores one into a **new** organization they own (never merged into an existing one); restores need a confirmed address when addresses are verified and are rate limited per user, and `data.json` is capped at `MAX_DATA_SIZE` since it's parsed in the request. The export is written to a file under `tmp/backups/` and streamed from there (deleted once sent), never built in memory. Members, users, encrypted API keys/tokens, and movement authors are left out. The importer copies rows with plain INSERTs (no ledger replay, no IPN/reference renumbering) and checks what the models would: every reference resolves inside the file, enumerated columns, acyclic trees; files are checked against each model's `attachment_limits` (recorded by `validates_attachment`). Columns follow the schema automatically, but **a new org-scoped table must be added to `OrganizationBackup::TABLES`** (dependency order, with its references) or it won't be backed up.
- **Organization reset & merge** (Settings → Danger zone, owners only, confirmed by typing the org name, which the server checks too): `Organization#reset_data!` destroys every `Organization::DATA_ASSOCIATIONS` record and keeps the org's settings, integrations, logo and members (IPN counter back to 1, catalog suppliers seeded again). `OrganizationMerge` moves a non-personal org into another org the user owns, in place (`update_all`, ids and ledger kept, so stock still matches its movements), resolving clashes as its class comment lists (same-name categories/footprints/tags/suppliers combined, parameters combined when name, type and unit match (else renamed "Name (2)"), parts with the same MPN/SKU/barcode folded together, zones never merged but taken codes renumbered, taken IPNs and references redrawn, members join with owners as admins), then destroys the source; one transaction. **A new org-scoped table must be handled in `OrganizationMerge`** (and in `DATA_ASSOCIATIONS` if `Organization` owns it directly).
- **Duplicate parts** (Inventory → Duplicates, `PartDuplicatesController`, writers merge): `PartDuplicates` groups parts sharing a part number (MPN, SKU, barcode or supplier SKU, compared without case/spaces/punctuation: "likely") or the same name + value + footprint / category + value + footprint ("possible"); "Not duplicates" stores every pair of the group as a `PartDuplicateDismissal` (lower id first). The inventory bulk bar's Merge opens the same page on the selection. `PartMerge` folds the duplicates into the kept part in one transaction (its class comment lists the rules: stock rows and ledger moved in place, order lines on the same order combined, supplier links and blank details filled, box & bag stock moved into the kept bag through the ledger) and refuses different units. `PartMerge.fold` is shared with `OrganizationMerge`: **a new table referencing parts must be handled in `PartMerge.fold`**.
- **Email notifications** (`NotificationDigestJob`, hourly in `config/recurring.yml`): a digest of low-stock parts and open orders past `expected_delivery` (`NotificationDigest`), sent from 8am in the org's time zone, daily or on Mondays (`Organization#notification_digest_due?`, `notifications_sent_on` keeps it to one per period). Admins switch each alert type and the frequency in Settings → Notifications (`notify_low_stock`, `notify_late_orders`, `notification_frequency`, carried by backups); each member opts out per organization from their profile (`OrganizationMembership#email_notifications`). Recipients are `Organization#notification_recipients` (access-granting, not opted out, confirmed when addresses are verified). Off with no SMTP (`config.x.email_notifications`, `NotificationDigest.available?`; `with_email_notifications(false)` in tests). Mail templates can replace the layout's account-action footer with `content_for :mailer_footer`.
- **Dashboard** (`DashboardController` → `DashboardSummary`): headline figures, 30 days of movements per local day (org time zone), a "Needs attention" list (late/shipped orders, out-of-stock and low parts, confirmed projects short of parts), low stock with quantities already on open orders, open orders, recent projects with buildability, most-used parts, categories and recent movements. A new feature worth surfacing there (loans, stocktakes…) adds a section to `DashboardSummary#as_props` and, if actionable, an `attention` item.
- **Activity log** (`ActivityEvent`, `ActivityController`, sidebar "Activity", admins only): a model opts in with `audited` (`Auditable` concern, included by `ApplicationRecord`; options `ignore:`, `secret:`, `on_create:`, `on:`), which logs create/update/destroy only while `Current.user` is set (`ApplicationController#set_current_user`, and `McpController` for write tools), so jobs, signups, seeds and the console write nothing. Updates store `{ attribute => [before, after] }` (foreign keys as the record's label under the association name, `secret:` attributes as nil, bookkeeping columns in `ignore:`; an update left with no change writes no event). Subjects are a plain `subject_type`/`subject_id` plus `subject_label`, not a polymorphic association. Bulk operations wrap their writes in `ActivityEvent.without_recording { }` and write one summary event with `ActivityEvent.record!` (CSV import, part merge, organization reset and merge, backup export and restore, IPN reassignment): do the same for any new bulk action. Child rows (order/BOM lines, part tags, suppliers, parameters) and stock movements (already a ledger) aren't audited. Deleting an organization logs nothing; a merge moves the source's events to the target; backups don't carry the log. Audit a new top-level model with `audited` and add its type to `ActivityController::SUBJECT_PATHS` and the page's `SUBJECT_TYPES`.
- **MCP server** (`POST /mcp`, `McpController` → `McpServer` / `McpServer::Tools`): stateless Streamable HTTP, JSON-RPC answered as plain JSON, tools scoped to the organization of the OAuth grant (`OauthAuthorization`), viewers included. Read tools (`McpServer::Tools`) are always listed; write tools (`McpServer::WriteTools`: stock in/out, move, count, create/update part, create draft project) only when the grant has the `mcp:write` scope ("Allow changes" on the consent page or Profile) **and** the user is still a writer (`OauthAuthorization#can_write?`, checked on every request). Writes go through the models (ledger movements signed with the user, reason suffixed "(via <client name>)") and never delete. OAuth 2.1 is built in (no gem): discovery at `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server` (`Oauth::MetadataController`, URLs from `request.base_url`), dynamic client registration (`OauthClient`, public clients, https or loopback redirect URIs, loopback ports ignored), consent page `oauth/authorize` (pick an organization), PKCE S256 required, refresh tokens rotate, only SHA-256 digests of codes/tokens are stored. Every call re-checks the user's active membership and lock. A 401 must carry `WWW-Authenticate: Bearer resource_metadata=…` (that's what starts Claude's sign-in). Profile lists connected apps (revocable). Grants are per user, so backups leave them out. Add a tool by extending `Tools::DEFINITIONS` (read) or `WriteTools::DEFINITIONS` (write) plus a private method of the same name.
- **KiCad HTTP library** (`/kicad/v1/…`, `KicadLibraryController` → `KicadLibrary`): read-only JSON in KiCad's format (every id and value a string, booleans `"True"`/`"False"`), authenticated by the organization's KiCad token (`Authorization: Token mskicad_…`; only its SHA-256 digest is stored on `organizations.kicad_token_digest`, issued/revoked by admins in Settings, left out of backups). A part is listed when a symbol resolves: `parts.kicad_symbol`, else `categories.kicad_symbol` up the tree, else `KicadLibrary::DEFAULT_SYMBOLS` matched on category names; obsolete parts never. The footprint is `parts.kicad_footprint` else `footprints.kicad_footprint`. KiCad keys symbols by name across the library, so duplicate part names get the IPN appended. Root URL ends in `/kicad/` (KiCad appends `v1/`; the bare paths answer too).
- **Vite gems and npm plugin move together**: `vite_ruby` checks the npm `vite-plugin-ruby` version at boot and refuses to start on a mismatch, so bump them in one change (and run the system tests). `rack-proxy` is only used by the Vite dev-server proxy in development.
- **Active Storage** is installed so `.destroy` on `Organization`, `Part`, `Footprint`, and `Supplier` (all declare attachments) works correctly.

## Testing
- **Every model, controller, and non-trivial piece of business logic must have tests.** When you add or change a model validation, scope, callback, or method — or a controller action — add or update the corresponding test in `test/` in the same change. Don't treat tests as optional or a follow-up; a feature isn't done until it's tested.
- Framework: Minitest 6 + fixtures (`test/test_helper.rb`), not RSpec. Shared factory-style helpers (`create_organization`, `create_part`, `create_order`, etc.) live in `test/test_helper.rb` — prefer them over hand-rolling setup. Minitest 6 has no bundled `minitest/mock`; use the `stub_singleton` helper.
- Run the suite with `bin/rails test` (add `test:system` for system tests) before considering work complete.
- In the test env Vite runs with `autoBuild: true` into `public/vite-test/`. The stalled/failed runs seen on 2026-10-07 came from parallel workers racing to rebuild a stale bundle (fixed: see the prebuild in `test_helper.rb`). Still wrap manual runs in a `timeout`, use `PARALLEL_WORKERS=1` to isolate a single file, and kill stray processes by PID rather than `pkill -f`.
- `test/system/scanner_camera_test.rb` can be flaky when the whole system suite runs (fake camera timing); rerun it alone before treating a failure as real.
- `test_helper.rb` builds the frontend once before parallel workers fork (they used to race rebuilding a stale bundle). Don't run `db:seed:replant` against the test DB before tests: the seeds collide with fixtures — `bin/rails db:test:prepare` resets it.
- Tests share `storage/test.sqlite3`: don't run two `bin/rails test` processes at once (`SQLite3::BusyException`).
